# Deploying GradientNovaAI to AWS

Everything here is Terraform (`infra/terraform`) plus one script (`scripts/deploy-aws.sh`). Nothing is created until you
run `terraform apply` yourself with your own AWS credentials, and `terraform destroy` removes it all again.

## What gets built

```
                       browser
                          │  https://dxxxx.cloudfront.net   (free HTTPS, no domain needed)
                    ┌─────▼──────┐   optional AWS WAF
                    │ CloudFront │──────────────────────────────┐
                    └─────┬──────┘                              │ /  (React app, cached at the edge)
       /api  /oauth2  /login/oauth2  /logout                    ▼
                          │ (secret header)               ┌───────────┐
                    ┌─────▼──────┐                        │ S3: site  │
                    │    ALB     │  only CloudFront can   └───────────┘
                    └─────┬──────┘  reach it
              ┌───────────┴───────────┐
        ┌─────▼─────┐           ┌─────▼─────┐      ECS Fargate, 2–10 tasks (ARM), auto scaling on CPU + requests
        │ API task  │    ...    │ API task  │      Spring Boot + ffmpeg
        └──┬──┬──┬──┘           └───────────┘
           │  │  └──────────── S3: content bucket (videos, PDFs, images; private; browsers upload video parts
           │  │                 straight to it with short-lived signed URLs)
           │  └─────────────── optional: ElastiCache Redis, Amazon MQ (RabbitMQ)
           └────────────────── RDS MySQL (private subnets, encrypted, daily backups)
```

Why it looks like this:

- **One address for everything.** CloudFront serves the site and forwards the API and Google-login paths to the load
  balancer. The browser sees a single HTTPS origin, so the session cookie is first-party and the free
  `*.cloudfront.net` certificate is enough. (This is the same shape the app already had behind Vercel's rewrites.)
- **The load balancer is not public in practice.** Its security group only admits CloudFront's address range and its
  listener rejects any request without CloudFront's secret header.
- **No stored AWS keys.** The app reads and writes S3 with its ECS task role. The database password is generated by RDS
  and kept in Secrets Manager; the Google secrets and the ticket-signing key live in one Secrets Manager secret. None of
  them is in the image, the repo, or the container's plain environment.
- **Tasks run in public subnets without a NAT gateway** (saves about $35/month per gateway). They get public IPs so they
  can reach ECR, Google and the AI provider; their security group only accepts the load balancer. The database is in
  subnets with no internet route at all.

## Before you start

1. An AWS account, and the CLI signed in: `aws sts get-caller-identity` should print your account.
2. Terraform 1.6+, Docker, Node 20+.
3. A Google OAuth client (Google Cloud Console → APIs & Services → Credentials → OAuth client ID, type *Web*). Note the
   client ID and secret. You'll add its redirect address after the first apply.

## First deploy

```bash
cd infra/terraform
cp terraform.tfvars.example terraform.tfvars      # fill in the Google client, admin email(s), region
terraform init
terraform plan                                     # read it; nothing is created yet
terraform apply
```

The first `apply` takes about 15 minutes (RDS and CloudFront are the slow parts). The ECS service will report that it
can't start tasks yet, because there is no image in ECR. That's expected. Then:

```bash
cd ../..
scripts/deploy-aws.sh          # builds and pushes the API image, uploads the React app, rolls the tasks
```

Finally tell Google where sign-in may return to. `terraform output` prints both values:

- **Authorized JavaScript origins:** `site_url`
- **Authorized redirect URIs:** `google_oauth_redirect_uri`

Open `site_url`, sign in with an email listed in `admin_emails`, and you're an admin. Nobody can become admin any other way.

Confirm the alarm-subscription email AWS sends if you set `alarm_email`.

### Releasing later

```bash
scripts/deploy-aws.sh          # both
scripts/deploy-aws.sh api      # backend only
scripts/deploy-aws.sh web      # frontend only
```

The backend rolls tasks one set at a time behind the load balancer, keeping the old ones until the new ones pass their
health check, and rolls back automatically if they never do. Database migrations (Flyway) run on startup.

## What it costs

Rough monthly figures for the defaults, in USD, region `ap-south-1`; check the AWS pricing pages and the AWS Pricing
Calculator for current numbers. Traffic-dependent items are the ones to watch.

| Item | Default | About |
|---|---|---|
| ECS Fargate, 2 × (1 vCPU, 2 GB, ARM) | always on | $55–65 |
| Application Load Balancer | always on | $20 |
| RDS MySQL `db.t4g.small`, 50 GB gp3, single zone | always on | $35 |
| Secrets Manager, CloudWatch logs and alarms | | $5–10 |
| CloudFront, S3 storage and requests | pay per use | a few $ at low traffic |
| **Baseline** | | **≈ $120–140** |

Optional add-ons: RDS Multi-AZ (+ ≈ $35), ElastiCache Redis `cache.t4g.micro` (≈ $13), Amazon MQ `mq.t3.micro`
(≈ $25), AWS WAF (≈ $10 + per request).

**Video traffic is the cost that scales.** Data transfer out to your learners is billed per GB, and videos are by far the
biggest thing you send. See *Scaling* below.

## Sizing for growth (the 100k-user goal)

100,000 registered users is usually a few thousand people online at once, not 100,000. The defaults handle small
hundreds comfortably; here is what to turn as you grow, in order:

| Symptom | Change |
|---|---|
| Tasks' CPU stays above ~55% | Auto scaling adds tasks up to `max_tasks` (10). Raise `max_tasks` and `task_cpu`/`task_memory`. |
| Database CPU or connections high | `db_instance_class` → `db.t4g.medium` / `db.m7g.large`; keep `max_tasks × db_pool_size` under its connection limit (the alarm warns at 120). |
| Sign-ins or rate limits behave differently per task | Set `enable_redis = true`: sessions, caches and rate limits become shared across tasks. |
| Question generation or video packaging slows the site | Set `enable_queue = true` so those jobs go through RabbitMQ, then move them to their own service (below). |
| Site goes down when one zone has trouble | `db_multi_az = true`. Tasks already run in two zones. |
| Bots or abuse | `enable_waf = true`. |

**The limitation to know about.** Today every video byte travels CloudFront → load balancer → an API task → S3, because
each video request is checked against the viewer's session ticket. That keeps the "viewers can't download" rules simple
and is fine into the thousands of viewers, but at large scale it makes video bandwidth and task count grow together.
The next step is to serve HLS segments to CloudFront straight from S3 using CloudFront signed cookies, so only the
small "may I watch this?" check hits the API. That is a separate change to the content-protection design, so it is
deliberately not part of this first deployment.

Also: ffmpeg packaging currently runs inside the web tasks. It is CPU-heavy, and the CPU alarm and auto scaling will
react, but a dedicated worker service consuming the queue is the cleaner long-term setup.

## Security notes

- TLS everywhere the browser is involved; HSTS is sent. Traffic from CloudFront to the load balancer is plain HTTP inside
  AWS's edge network, protected by the secret header and the CloudFront-only security group. Serving your own domain from
  the load balancer over HTTPS is the upgrade path once you have one.
- The content bucket and site bucket are private (no public access, encrypted, site bucket readable only through the
  CloudFront distribution). The content bucket is reachable only by the task role and by short-lived signed upload URLs.
- Terraform state contains the Google secret and generated passwords. Keep `terraform.tfstate` and `terraform.tfvars`
  private (both are git-ignored), or move state to an encrypted S3 backend (see `versions.tf`).
- AWS limits a security group to 60 rules by default and CloudFront's address list uses about 55 of them. That fits, but
  if `terraform apply` complains, ask AWS Support to raise the "rules per security group" quota.

## Tearing it all down

```bash
cd infra/terraform
# 1. lets the database be deleted (skips the protection flag) and lets terraform empty the content bucket:
terraform apply -var db_deletion_protection=false -var force_destroy_buckets=true
terraform destroy
```

That deletes the database (a final snapshot is skipped unless deletion protection was on) and every uploaded file.
Back up what you want to keep first. The image repository, both buckets, the CloudFront distribution and all networking
are removed. Billing stops when the resources are gone; double-check the RDS, ECS and CloudFront pages afterward.

## Cheap development profile

While nobody is using it, deploy the small profile instead of the defaults:

```bash
cd infra/terraform
cp dev.tfvars.example dev.tfvars     # add the Google client and your admin email
terraform apply -var-file=dev.tfvars
```

It runs one small task and a micro database: roughly $55–70/month left on, and about $0.10/hour, so you can
`terraform destroy -var-file=dev.tfvars` after a demo and apply again later (the database and uploads are deleted with
it, so keep anything you care about in the real local database). Storage for a few GB and light traffic add only
cents. The ALB (about $20/month) and the Fargate task are the largest parts of the bill; there's no way to make those
free while the site is up.

When the company takes over, they run the normal `terraform.tfvars` with the launch sizing described above.
